# Managing an instance

Below is a number of high-level principles for managing a physical HWaaS instance.
It's worth noting that HWaaS units are generally managed with physical, on-prem access.

Maintainers will need to be able to connect machines under test, add new `remote-hands` instances,
have physical switch access, etc.

## Hardware Requirements

### Gateway

#### Components

The Gateway server is the monolithic entry-point for a HWaaS instance. It contains a number
of components, such as:

- Reverse Proxy
- Context API
- WS Proxy Gateway
- Web UI Hosting
- SQLite Database
- NFS Image Store

#### Recommend Specifications

Due to the virtualization, high network traffic, and various workloads, we recommend the following minimum specifications for production workloads:

- Xeon Silver 4410Y or equivalent x86 CPU
- 32 GB ECC DDR4 RAM
- 512GB+ SSD (you may need more, depending on the number and size of images hosted)
- Dual port 10GbE PCIe adapter

### Networking

The HWaaS supports a two switch setup, with the following requirements:

- A managed VLAN switch
- A managed VLAN switch with VRF support, used for managing BMR networks

#### Onboarding

For more complete onboarding and `netctl` guidelines, see the hardware [onboarding guide](../aruba-switch).

#### Custom Implementations

We currently only support the HP Aruba Switch series, yet it is somewhat trivial
to onboard new routers, provided one can implement the following trait bounds.

```rust
pub trait Api {
    async fn get_ports(&self) -> Result<Vec<PortRepresentation>, SwitchApiError>;
    async fn add_untagged_port(&self, vlan_id : &VlanID, port_id : &PortID) -> Result<(), SwitchApiError>;
    async fn remove_port(&self, port_id : &PortID) -> Result<(), SwitchApiError>;
}
```

Which is expected to provide the following information:

- get_ports: Request list of all ports of a switch. Fails when request is invalid or switch is unreachable. On success returns a data structure containing information about a port.
- add_untagged_port: Add a port to a VLAN in Untagged mode. Implicitly enables the port. Fails when receiving an invalid ID. Idempotent to redundant adding/enabling.
- remove_port: Disables the port given by port_id. Implicitly removes it from the VLAN it belonged to prior. Idempotent to redundant disabling.

### Power Management

The requirements for a managed power switch are minimal. Effectively, you need to be able to
write and deploy a bash or similar script that can be invoked to toggle a machines power state.

This is eventually passed as a script invoked by each individual `remote-hands` instance for managing their own power.

### Remote Hands

We currently are targetting the Raspberry Pi 4 for the `remote-hands` instances.

This is because of the following requirements:

- USB OTG Support (essential for USB MASS booting)
- Power over Ethernet
- Affordable and easily sourceable

In theory, there is no strong requirement to run the `remote-hands` services on Raspberry Pi specifically.
If you can meet the above requirements, you can deploy on other platforms as well.

#### Individual components

Each `remote-hands` instance requires the following physical components:

- Serial to USB adapter
- V4L capture card for MJPEG streaming
- Raspberry Pi PoE header (provides power while keeping USB OTG available)
- USB Power Blocker (prevents Pi from potentially powering on the BMR)

### Bare Metal Resources

Bare metal resources have a number of optional and required interfaces.

| Component          | Necessary | Description                                                                                                           |
| ------------------ | --------- | --------------------------------------------------------------------------------------------------------------------- |
| USB                | Required  | Handles image booting, as well as remote keyboard and mouse.                                                          |
| Controllable Power | Requried  | Machines should **not** go into sleep, but rather have a hard shutdown.                                               |
| Ethernet           | Optional  | Necessary for machine network access, but you can boot a machine without that machine having a physical network port. |
| Serial Connection  | Optional  | Serial support is convenient, especially for boot debugging, but not required.                                        |
| Video Out          | Optional  | Video out can be captured with various adapters + V4L devices. This is not a required component.                      |

## Deployment

Deployment is most easily handled with Nix as well. We suggest using `colmena`, or the native `nixos-rebuild` tools for
building and pushing system configurations.

These deployments can be quite large, and require cross compilation using `binfmt` for the `remote-hands` instances.

## Maintainer CLI

The `machine-ops` CLI is used to interact with the HWaaS database and run CRUD operations for registering machines.
Before the Context API can hand out machines to users, each bare metal resource must be registered in the database
with its associated remote-hands service URLs and switch port mappings.

### Registering machines

Machine data is provided as a JSON array. Each entry describes a single BMR and its connections to
remote-hands services and network switches.

**This is typically handled in the `nix` configuration, and not something maintainers will have to roll themselves.**

```json
[
  {
    "id": 1,
    "platform": "Intel-NUC-x86_64",
    "remote_power": "http://ts-bmr1:8082/power",
    "remote_usb": "http://ts-bmr1:8080/usb",
    "remote_serial": "http://ts-bmr1:8081/serial",
    "remote_auxiliary": "http://ts-bmr1:8083/auxiliaries",
    "remote_mjpeg": "http://ts-bmr1:8084",
    "switch_connections": {
      "lan0": {
        "switch": "switch-a",
        "port": "5"
      }
    }
  }
]
```

<Callout type="note">
  The `switch` value in `switch_connections` must match a switch name defined in
  your NetCtrl inventory configuration. The `port` value must correspond to a
  physical port on that switch.
</Callout>

## Secrets Management

The HWaaS uses [SOPS](https://github.com/getsops/sops) to manage secrets throughout the repository.
This covers switch credentials, deployment keys, and any other sensitive configuration.

SOPS is not a hard requirement, and can be replaced with another secrets management solution, provided no secrets are written to the `nix` store.

### Initial setup: create AGE keys

You can derive AGE keys from an existing SSH key for convenience:

```sh
# Print your public AGE key (add this to .sops.yaml)
cat ~/.ssh/id_ed25519 | ssh-to-age

# Print your private AGE key
cat ~/.ssh/id_ed25519 | ssh-to-age -private-key
```

<Callout type="warning">
    Only `ssh-rsa` and `ssh-ed25519` keys are supported for AGE conversion. If you don't have one of these,
    generate a standalone AGE key instead:

    ```sh
    age-keygen -o ~/.config/sops/age/keys.txt
    age-keygen -y ~/.config/sops/age/keys.txt  # prints the public key
    ```

</Callout>

Save the private key and optionally export its path so SOPS can find it:

```sh
mkdir -p $HOME/.config/sops/age
echo "AGE-SECRET-KEY-..." > $HOME/.config/sops/age/keys.txt

# Optional — only needed if you use a non-default path
export SOPS_AGE_KEY_FILE=$HOME/.config/sops/age/keys.txt
```

### Basic operations

When working with SOPS, you are effectively updating the secrets in the repository for all users with access.

Here are a number of operations that will allow you to do so:

```sh
# Rotate/update keys after .sops.yaml changes
sops updatekeys secrets/*

# Encrypt files in place
sops encrypt --age <your-public-key> -i ./secrets/*

# Decrypt files in place
sops decrypt -i secrets/*
```

### Adding a new admin

1. Have the new admin generate their public AGE key using the steps above.
2. Add their key to `.sops.yaml`:

```yaml
keys:
  - &admin_alice age1wduyz0jrac8hynner3...
  - &instance_gateway age1rjmf88mleas5x7dzfh...
creation_rules:
  - path_regex: secrets/[^/]+\.(yaml|json|env|ini)$
    key_groups:
      - age:
          - *admin_alice
          - *instance_gateway
```

3. Apply the changes:

```sh
sops updatekeys secrets/*
```

### Adding a server instance

Retrieve the instance's AGE key from its SSH host key, add it to `.sops.yaml` using the same pattern
as above, and run `sops updatekeys secrets/*`.

```sh
ssh-keyscan <hostname> | ssh-to-age
```

## SSH Configuration

<Callout type="warning">
  This is actively being refactored, and may soon be out of date.
</Callout>

The following SSH configuration patterns are useful for managing a HWaaS instance. Because terminal servers
(Raspberry Pis) are typically accessed through a gateway jump host, a well-structured SSH config avoids
repetitive connection details.

```ssh-config
# Gateway — the main entry point
HOST my-instance
  User admin
  Hostname gateway.example.com
  Port 22
  PreferredAuthentications publickey
  IdentityFile ~/.ssh/id_ed25519

# Terminal servers — wildcard matches all BMRs
HOST ts-bmr*
  User hwaasadmin
  Hostname %h.internal.example.com
  Port 22
  ProxyJump my-instance
  PreferredAuthentications publickey
  IdentityFile ~/.ssh/id_ed25519
  StrictHostKeyChecking accept-new

# WebSocket gateway
HOST ws-gateway
  User admin
  Hostname 10.0.0.123
  Port 22
  ProxyJump my-instance
  PreferredAuthentications publickey
  IdentityFile ~/.ssh/id_ed25519
  StrictHostKeyChecking accept-new
```

<Callout type="note">
  The `%h` token in `Hostname` is expanded at runtime to the host you specify on
  the command line. Combined with the `*` wildcard in the `HOST` pattern, a
  single config block covers all terminal servers. For example, `ssh ts-bmr3`
  connects to `ts-bmr3.internal.example.com` via the gateway.
</Callout>

If you manage auxiliary devices, each one needs its own entry because they connect through a specific
terminal server:

```ssh-config
HOST aux0
  User root
  Hostname aux0
  ProxyJump ts-bmr21
  PreferredAuthentications publickey
  IdentityFile ~/.ssh/id_ed25519
  UserKnownHostsFile /dev/null
  StrictHostKeyChecking accept-new
```

## Configuration Reference

### Context API configuration

The Context API is configured in Nix, and then deserialized from a JSON file.

Below are the key fields and their defaults.

```json
{
  "context_lifetime": 3600,
  "context_max_lifetime": 7200,
  "db_file_path": "/var/lib/contextapi/db.sqlite",
  "max_db_connections": 9,
  "net_ctrl_base_path": "http://127.0.0.1:8000",
  "network_gateway": {
    "ws_gateway_url": "ws://10.0.0.123:8080"
  },
  "image_api_settings": {
    "max_file_size": "5 GB",
    "store": "/var/lib/contextapi/images"
  },
  "remote_max_request_size": 67108864,
  "remote_oas_paths": [],
  "request_timeouts": {
    "context_management_api": 120000,
    "image_api": 120000,
    "single_context_api": 60000
  }
}
```

| Field                              | Default          | Description                                                                      |
| ---------------------------------- | ---------------- | -------------------------------------------------------------------------------- |
| `context_lifetime`                 | `3600`           | Default context lifetime in seconds                                              |
| `context_max_lifetime`             | `7200`           | Maximum lifetime a user can extend to                                            |
| `db_file_path`                     | _required_       | Path to the SQLite database                                                      |
| `max_db_connections`               | `9`              | Max DB connection pool size (defaults to 1/4 of available parallelism)           |
| `net_ctrl_base_path`               | _required_       | Base URL for the NetCtrl service                                                 |
| `network_gateway.ws_gateway_url`   | _required_       | WebSocket gateway URL                                                            |
| `image_api_settings.max_file_size` | _required_       | Maximum upload size ([ByteSize](https://docs.rs/bytesize) format, e.g. `"5 GB"`) |
| `image_api_settings.store`         | _required_       | Filesystem path for image storage (typically an NFS export)                      |
| `remote_max_request_size`          | `67108864`       | Max request body size forwarded to remote-hands (bytes)                          |
| `request_timeouts.*`               | `60000`-`120000` | Per-API request timeouts in milliseconds                                         |

### NetCtrl inventory

The network controller needs an inventory of your managed switches.

This is also typically constructed via Nix, but here is an example of the schema:

```json
{
  "switch-a": {
    "model": "aruba",
    "ip": "192.168.1.11",
    "port": 80,
    "credentials": {
      "username": "hwaas",
      "password": "changeme"
    },
    "default_vlan": { "vlan_id": 1 },
    "mgmt_vlan": { "vlan_id": 42 },
    "critical_ports": {
      "mgmt_ports": ["1", "2"],
      "trunk_ports": ["23", "24"]
    }
  }
}
```

| Field                        | Description                                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `model`                      | Switch type: `aruba`, `aruba2540`, `aruba-aos-cx`, `aruba-cx6100`, `fs-picos`, `dummy`, `dummy24`, `dummy48` |
| `ip`                         | Management IP address of the switch                                                                          |
| `port`                       | REST API port (optional, uses default if omitted)                                                            |
| `credentials`                | Username and password for REST API authentication (optional for unprotected switches)                        |
| `default_vlan`               | The default/native VLAN ID                                                                                   |
| `mgmt_vlan`                  | Management VLAN ID (protected from modification by NetCtrl)                                                  |
| `critical_ports.mgmt_ports`  | Ports that should never be modified (management uplinks)                                                     |
| `critical_ports.trunk_ports` | Trunk ports that carry tagged traffic between switches                                                       |

## NixOS Module Options

All HWaaS services are available as NixOS modules. Below is a summary of the available options for each service.

### Gateway services

#### Context API (`services.contextApi`)

```nix
{
  services.contextApi = {
    enable = true;
    address = "0.0.0.0";      # Listen address
    port = 8080;               # Listen port
    config = { /* ... */ };    # Context API config (attribute set or path)
    otelEndpoint = "http://127.0.0.1:4317";  # OpenTelemetry collector
    consoleAddress = null;     # Tokio console address (e.g. "127.0.0.1:6669")
    openFirewall = false;      # Automatically open firewall port
  };
}
```

#### Network Controller (`services.netCtrl`)

```nix
{
  services.netCtrl = {
    enable = true;
    address = "0.0.0.0";
    port = 8000;
    inventory = { /* switch inventory attrset */ };
    otelEndpoint = "http://localhost:4317";
    enableLogFile = true;
    openFirewall = false;
  };
}
```

### Remote-hands services

Each remote-hands service follows the same pattern. These run on the Raspberry Pi terminal servers.

<Callout type="note">
  Remote-hands services all share a common set of options: `enable`, `address`,
  `port`, `configFile`, `otelEndpoint`, `consoleAddress`, and `openFirewall`.
  The `remote-serial` service additionally exposes `serialConfig` for baud rate
  and line settings.
</Callout>

#### Remote USB (`services.remote-usb`)

```nix
{
  services.remote-usb = {
    enable = true;
    address = "0.0.0.0";
    port = 8080;
    configFile = "/etc/hwaas/remote-usb.json";
    openFirewall = true;
  };
}
```

#### Remote Serial (`services.remote-serial`)

```nix
{
  services.remote-serial = {
    enable = true;
    address = "0.0.0.0";
    port = 8081;
    configFile = "/etc/hwaas/remote-serial.json";
    serialConfig = {
      baud_rate = 115200;
      char_size = 8;       # 5, 6, 7, or 8
      parity = "none";     # "odd", "even", or "none"
      stop_bits = 1;       # 1 or 2
    };
    openFirewall = true;
  };
}
```

#### Remote Power (`services.remote-power`)

```nix
{
  services.remote-power = {
    enable = true;
    address = "0.0.0.0";
    port = 8082;
    configFile = "/etc/hwaas/remote-power.json";
    openFirewall = true;
  };
}
```

#### Remote Auxiliary (`services.remote-auxiliary`)

```nix
{
  services.remote-auxiliary = {
    enable = true;
    address = "0.0.0.0";
    port = 8083;
    configFile = "/etc/hwaas/remote-auxiliary.json";
    openFirewall = true;
  };
}
```

#### Remote MJPEG

Remote MJPEG is slightly different, it is simply an MJPEG streamer, which is then proxied through the `contextapi`.

You can create your own custom `gstreamer` or `ffmpeg` pipeline, but `usteamer` is quite straightforward and handles changes in resolution automatically (if your capture card supports it).

```nix
{
    services.ustreamer = {
        enable = true;
        device = "/dev/videoMUT"; # udev rule applied for naming
        listenAddress = "0.0.0.0:8085";
        extraArgs = [
        "--format=yuyv"
        "--resolution=1280x720"
        "--workers=3"
        "--persistent"
        "--drop-same-frames=30"
        ];
    };
}
```

## Deploying Remote-Hands (Raspberry Pi)

Each terminal server runs NixOS on a Raspberry Pi 4. Setup is a two-step process.

### Step 1: Boot the generic NixOS image

Download the latest aarch64 SD image from [NixOS Hydra](https://hydra.nixos.org/job/nixos/trunk-combined/nixos.sd_image.aarch64-linux)
and write it to a USB stick (preferred over SD cards for speed):

```sh
dd if=nixos-sd-image-*.img of=/dev/sdX bs=4M status=progress
```

Boot the Pi and let it resize partitions on first boot.

<Callout type="warning">
    Many Raspberry Pi 4 units ship with firmware that cannot boot from USB. If your Pi doesn't boot
    from USB, write the image to an SD card first, boot it, then update the firmware:

    ```sh
    nix-shell -p raspberrypi-eeprom
    mount /dev/disk/by-label/FIRMWARE /mnt
    BOOTFS=/mnt FIRMWARE_RELEASE_STATUS=stable rpi-eeprom-update -d -a
    ```

    <a href="https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#boot_order-fields">You can read more about the various boot order options here</a>

    Reboot and let it flash itself, then you can switch to USB boot.

</Callout>

### Step 2: Deploy the final configuration

Deploy your NixOS configuration to the Pi. This can be done locally on the Pi:

```sh
nixos-rebuild switch --flake .#ts-bmr1
```

Or remotely from your workstation:

```sh
nixos-rebuild switch --flake .#ts-bmr1 \
  --target-host ts-bmr1 \
  --build-host localhost \
  --use-remote-sudo
```

<Callout type="note">
    Building aarch64 packages on an x86 workstation requires binfmt emulation. Add this to your
    NixOS configuration:

    ```nix
    boot.binfmt.emulatedSystems = [ "aarch64-linux" ];
    ```

    This uses QEMU to transparently run aarch64 binaries. It's **much** slower than native compilation but
    reliable for deployment builds.

</Callout>

## Binary Cache

We strongly suggest using a binary cache when building this project, in order to ensure reasonable build times.

Cross-compilation for the `remote-hands` services is particularly painful, and can result on full day builds even with strong hardware.

## Monitoring

We suggest working with a `grafana` based stack. More content will be available when we create our
reference deployments, but the following architecture has proved succesful for the time being.

- `tempo` - responsible for various traces that can occur within the HWaaS
- `prometheus` - Capable of exporting machine resource health, systemd service health, and more
- `loki` - handles log aggregation

## Security

There are a few key points for any administrator looking to manage a HWaaS instance.

- The HWaaS is not a multi-tenant solution, and does not have an authentication system.
  We recommend using a VPN to encapsulate each instance.
- Anyone with a `context-id` can mutate the machines under test; they can change BIOS/UEFI settings, power them on and off, etc.
- Anyone with access to the gateway server or monitoring stack can enumerate the contexts in use. Context hashes provide separation, not secrecy: they are not treated as credentials, are not hashed with a password-grade algorithm (e.g. BCrypt or Argon2), and may appear in logs. Do not rely on a context-id being confidential.
