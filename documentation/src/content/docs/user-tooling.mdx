## Tutorials

### Running your first test with HWaaS

In this tutorial, we will create and run a test with HWaaS through the HWaaS User Tooling.
To follow this tutorial, we need:

- A working HWaaS instance with at least one configured BMR
- A machine with [the `nix` package manager][a0] installed

As a first step, we set up a `nix` project to run our test from.
Run the following commands:

```bash
nix --extra-experimental-features "flakes nix-command" flake new \
    my-first-hwaas-test -t 'github:secunet-AG/hwaas#simple'
cd my-first-hwaas-test
```

Next, we must review and modify settings to connect the test with our HWaaS instance.
This requires knowledge of two things: The HWaaS API URL and a valid _Platform Identifier_.
In this tutorial, we assume that the HWaaS API URL is:

```text
https://api.hwaas.my-corp.example/v5/
```

In practice, we would ask the administrator of our HWaaS instance for the configured API URL.
We open the file `hwaas-test.nix` with our `$EDITOR` and replace the quoted string after `apiUrl =` with the URL shown above.
The end result can look like this:

```nix
apiUrl = "https://api.hwaas.my-corp.example/v5/";
```

Next, we determine a suitable Platform Identifier.
For this tutorial we assume that somebody told us the platform identifier is `amd64_test-machine`.
If you do not know what platform identifier to choose, [refer to our HowTo-Guide on the topic][a2].
We open `hwaas-test.nix` with our `$EDITOR` once more and replace the quoted string after `platform =` with the Platform Identifier chosen previously.
The end result can look like this:

```nix
dummy1 = {
  platform = "amd64_test-machine";
  # ...
};
```

Next, we build the test to produce a `result/` output:

```bash
# NOTE: The '.driver' at the end is important!
nix build .#checks.x86_64-linux.my-first-hwaas-test.driver
```

Finally, we run the actual test:

```bash
./result/bin/nixos-test-driver
```

And that's it!
If the test exits with a status code of 0, you have successfully run your first test on a HWaaS instance.

[a0]: https://nixos.org/
[a1]: https://nix.dev/tutorials/nixos/integration-testing-using-virtual-machines


## How-To Guides

### How to Determine a Suitable Platform Identifier for a HWaaS Test

In this How-To Guide, we will choose a suitable Platform Identifier for a HWaaS test.
We assume that the HWaaS API URL is:

```text
https://api.hwaas.my-corp.example/v5/
```

To get a list of all valid Platform Identifiers in your HWaaS instance, run the following command:

```bash
curl -sS https://api.hwaas.my-corp.example/v5/inventory | \
    jq -er 'map(.properties.platform) | sort | .[]'
```

If the list of platform identifiers doesn't help you choose the correct platform, ask a colleague or your HWaaS administrator for help.
At the moment, it's not possible to obtain additional information about test machines beyond their platform identifiers.
Progress on enabling HWaaS to provide additional information about test platforms is tracked on GitHub: <https://github.com/secunet-AG/hwaas/issues/203>.


## Reference

### Platform Identifiers

The Platform Identifier identifies Bare Metal Resources from the inventory of a HWaaS instance.
Platform Identifiers can, but need not be unique strings.
This allows HWaaS instances to dynamically scale the amount of Bare Metal Resources available under a given Platform Identifier.
A HWaaS test requiring a Bare Metal Resource with a given Platform Identifier will wait until any matching resource becomes available.
In contrast to assigning tests to a fixed, pre-determined Bare Metal Resource, using Platform Identifiers improves device utilization and makes device maintenance easier.


## Explanation

### About NixOS Test Integration

The HWaaS User Tooling was born out of the desire to integrate HWaaS in an environment previously using NixOS tests.
As NixOS tests use Python to define the test script and helper methods already, implementing HWaaS User Tooling as Python module was an obvious choice.
This allowed the code interacting with HWaaS to integrate seamlessly into preexisting test scripts.

In addition, the HWaaS User Tooling was never meant to be a standalone tool for interacting with HWaaS.
It doesn't have a standalone CLI and standalone installation isn't possible either.
While this could be changed, previous applications of HWaaS User Tooling haven't required it.

Among the benefits of having HWaaS User Tooling integrate with NixOS Tests are:

- _Reproducible tests from start to finish_:
  All code to ensure a reproducible test result (down to individual source files) is contained in a single NixOS test.


## Troubleshooting

### Name resolution fails

If you see any of these messages:

- `Temporary failure in name resolution`
- `Failed to resolve '...'`
- `Max retries exceeded with url: /v5/contexts`

It means that the HWaaS setup code running inside the Test VM cannot resolve the hostname of your HWaaS instance.
The most common causes for this are:

- **Running a HWaaS test as top-level `check`/`package` attribute**:
    - _Diagnosis_: You're running your test like:
        ```bash
        nix build .#checks.x86_64-linux.my-first-hwaas-test
        ```
        instead of:
        ```bash
        nix build .#checks.x86_64-linux.my-first-hwaas-test.driver
        ./result/bin/nixos-test-driver
        ```
    - _Solution_: Instead of building the test installable itself, build the `driver` attribute and
      run the resulting test script like this:
        ```bash
        nix build .#checks.x86_64-linux.my-first-hwaas-test.driver
        ./result/bin/nixos-test-driver
        ```
- **Invalid `apiUrl` value**:
    - _Diagnosis_: You forgot to edit the `apiUrl` parameter after creating a test from a template.
      Or you mistyped the `apiUrl` parameter while editing it.
    - _Solution_: Double-check the value of the `apiUrl` parameter in the failing test.
      You can run the following command (with your value for `apiUrl`) to ensure the HWaaS API URL
      is valid:
        ```bash
        curl -L "${YOUR_API_URL}/inventory"
        ```

If none of the above helps, the issue is probably outside of your HWaaS test.

### My test shows no output

In this case your test is probably stalled/frozen waiting for some event to happen.
You can get some amount of extra debug output by calling `nixos-test-driver` with extra arguments, like so:

```bash
nix build .#checks.x86_64-linux.my-first-hwaas-test.driver
LOGLEVEL="debug" ./result/bin/nixos-test-driver
```

If this doesn't help diagnose your problem, you can try to summon an interactive debugger in your test script.
To achieve this, inject a fault at the desired location of your tests `testScript` and set `enableDebugHook`, like so:

```nix
{
  # ...
  enableDebugHook = true;
  testScript = ''
  raise Exception("forced error")
  # ...remainder of your test script...
  '';
}
```

Then execute the test driver with an extra argument like so:

```bash
./result/bin/nixos-test-driver --debug-hook-attach "echo"
```

And wait for the following output to appear:

```text
!!! Breakpoint reached, run ...
RemotePdb session open at 127.0.0.1:4444, waiting for connection ...
```

<Callout type="note">
    Do not run the command advertised in the output above. It's just a stub to get the interactive
    debugger to kick in.
</Callout>

{/*
Maintainer note: Using the real `attach` command from the `breakpointHook` here will not work, since
that attempts to enter the test namespace. HWaaS tests run outside of a sandbox, so the `attach`
script will fail.
*/}

Now, in a separate shell, run the following command:

```bash
nix-shell -p socat --command 'socat readline tcp:127.0.0.1:4444'
```

Due to how the debugger works, you cannot see the actual test script in the debugger.
However, the fully assembled test script is available under `./result/test-script`, like so:

```bash
less ./result/test-script
```

Here are a few useful commands for use in the interactive Debugger to get you going:

```python3
# Get the names of all variables/functions defined in the test
print(symbols.keys())
# Print the `controlVM` test variable
print(symbols["controlVM"])
```
