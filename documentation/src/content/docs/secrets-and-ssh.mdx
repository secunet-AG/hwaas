# Secrets & SSH

This page covers managing secrets across the repository with SOPS, and the SSH
configuration patterns that make it easier to reach the [Gateway](./core-concepts#gateway)
and each [`remote-hands`](./core-concepts#remote-hands) terminal server.

import Callout from "../../components/Callout.astro";

## Secrets Management

The HWaaS uses [SOPS](https://github.com/getsops/sops) to manage secrets throughout the repository.
This covers switch credentials, deployment keys, and any other sensitive configuration.

SOPS is not a hard requirement, and can be replaced with another secrets management solution, provided no secrets are written to the `nix` store.

<Callout type="danger">
  Never write secrets into the `nix` store. Anything in the store is
  world-readable on the machine and may be copied to a binary cache. Always
  route sensitive values through SOPS (or your chosen secrets manager) at
  runtime.
</Callout>

### Initial setup: create AGE keys

You can derive AGE keys from an existing SSH key for convenience:

```sh
# Print your public AGE key (add this to .sops.yaml)
cat ~/.ssh/id_ed25519 | ssh-to-age

# Print your private AGE key
cat ~/.ssh/id_ed25519 | ssh-to-age -private-key
```

<Callout type="warning">
    Only `ssh-rsa` and `ssh-ed25519` keys are supported for AGE conversion. If you don't have one of these,
    generate a standalone AGE key instead:

    ```sh
    age-keygen -o ~/.config/sops/age/keys.txt
    age-keygen -y ~/.config/sops/age/keys.txt  # prints the public key
    ```

</Callout>

Save the private key and optionally export its path so SOPS can find it:

```sh
mkdir -p $HOME/.config/sops/age
echo "AGE-SECRET-KEY-..." > $HOME/.config/sops/age/keys.txt

# Optional — only needed if you use a non-default path
export SOPS_AGE_KEY_FILE=$HOME/.config/sops/age/keys.txt
```

### Basic operations

When working with SOPS, you are effectively updating the secrets in the repository for all users with access.

Here are a number of operations that will allow you to do so:

```sh
# Rotate/update keys after .sops.yaml changes
sops updatekeys secrets/*

# Encrypt files in place
sops encrypt --age <your-public-key> -i ./secrets/*

# Decrypt files in place
sops decrypt -i secrets/*
```

### Adding a new admin

1. Have the new admin generate their public AGE key using the steps above.
2. Add their key to `.sops.yaml`:

```yaml
keys:
  - &admin_alice age1wduyz0jrac8hynner3...
  - &instance_gateway age1rjmf88mleas5x7dzfh...
creation_rules:
  - path_regex: secrets/[^/]+\.(yaml|json|env|ini)$
    key_groups:
      - age:
          - *admin_alice
          - *instance_gateway
```

3. Apply the changes:

```sh
sops updatekeys secrets/*
```

### Adding a server instance

Retrieve the instance's AGE key from its SSH host key, add it to `.sops.yaml` using the same pattern
as above, and run `sops updatekeys secrets/*`.

```sh
ssh-keyscan <hostname> | ssh-to-age
```

## SSH Configuration

<Callout type="warning">
  This is actively being refactored, and may soon be out of date.
</Callout>

The following SSH configuration patterns are useful for managing a HWaaS instance. Because terminal servers
(Raspberry Pis) are typically accessed through a gateway jump host, a well-structured SSH config avoids
repetitive connection details.

```ssh-config
# Gateway — the main entry point
HOST my-instance
  User admin
  Hostname gateway.example.com
  Port 22
  PreferredAuthentications publickey
  IdentityFile ~/.ssh/id_ed25519

# Terminal servers — wildcard matches all BMRs
HOST ts-bmr*
  User hwaasadmin
  Hostname %h.internal.example.com
  Port 22
  ProxyJump my-instance
  PreferredAuthentications publickey
  IdentityFile ~/.ssh/id_ed25519
  StrictHostKeyChecking accept-new

# WebSocket gateway
HOST ws-gateway
  User admin
  Hostname 10.0.0.123
  Port 22
  ProxyJump my-instance
  PreferredAuthentications publickey
  IdentityFile ~/.ssh/id_ed25519
  StrictHostKeyChecking accept-new
```

<Callout type="note">
  The `%h` token in `Hostname` is expanded at runtime to the host you specify on
  the command line. Combined with the `*` wildcard in the `HOST` pattern, a
  single config block covers all remote-hands. For example, `ssh ts-bmr3`
  connects to `ts-bmr3.gateway.example.com` via the gateway.
</Callout>

If you manage auxiliary devices, each one needs its own entry because they connect through a specific
remote-hands:

```ssh-config
HOST aux0
  User root
  Hostname aux0
  ProxyJump ts-bmr21
  PreferredAuthentications publickey
  IdentityFile ~/.ssh/id_ed25519
  UserKnownHostsFile /dev/null
  StrictHostKeyChecking accept-new
```
